### Terms

- **Relationship** means an Access relationship with referential integrity; it is not an index.
- **Normal index** permits duplicate values and accelerates a lookup.
- **Unique index** rejects duplicate non-null keys and is proposed only where a verified candidate-key rule exists.
- **Composite index** orders two or more fields for a demonstrated multi-column predicate; field order must match the query.
- **NEEDS BUSINESS CONFIRMATION** means no constraint may be deployed until the named rule is approved.

Risk is the migration/data-integrity risk of the proposed action: **High**, **Medium**, or **Low**. “Data affected” describes the possibility even though this planning commit changes no data.

## 2. Mandatory safety and Access 2016 deployment protocol

Before **every** structural change: (1) obtain exclusive access and record the source database path, size, timestamp, Access bitness and file format; (2) make a byte-for-byte backup outside the repository and prove it opens; (3) export table definitions, relationships, indexes, row counts, and validation-query results; (4) compact/repair a copy; (5) rehearse on that copy with DAO/ACE used by Access 2016; (6) execute each DDL statement separately inside the safest supported transaction boundary; (7) re-run orphan/duplicate/null/length/domain checks and compare row counts/totals; (8) test the real forms, queries and import fixture; and (9) retain a rollback copy and signed result log. A failure restores the backup—never “fix” data in place without an approved exception report.

Access-specific rules: use `LONG` foreign keys for `AUTOINCREMENT` parents; bracket `[Status]` and other ambiguous names in queries; do not assume a multi-statement SQL file is atomic; keep text indexes within ACE index limits and test them with the actual collation/data; use `CURRENCY` for exact monetary values; recognize that `INTEGER` is 16-bit and `BYTE` is 0–255; and set defaults/Required properties through an Access-verified migration mechanism. Cascading deletes are **not proposed** anywhere. Cascade updates are unnecessary for AutoNumber keys.

## 5. Highest-risk issues and compatibility blockers

Highest-risk issues are the unverified live schema; possible data loss/error 3163 from field-size mismatch; adding RI over orphans; absent import-session boundary; ambiguous payment attachment; unresolved bank-account/import-batch parents; renewal- and payment-status conversions; and applying Required/default/unique rules to unknown legacy data.

The current **Access 2016 compatibility blockers** are: no execution proof against Access 2016/ACE; unknown live object definitions; ambiguous duplicate-012 run order; multi-statement DDL execution assumptions; reserved `[Status]` usage; Long/AutoNumber compatibility requiring verification; 16-bit INTEGER/BYTE limits; Long Text not being eligible for ordinary indexing; and unknown hidden dependencies in forms/queries/VBA. DB-01, DB-03 and DB-14 must clear these before Phase 4.

## 6. Business confirmations required

The following decisions are explicitly unresolved: import-session/error/log ownership and retention; role optionality; self-parent roots; policy branch/company consistency and marketer/branch nullability; payment-to-policy/installment cardinality; follow-up/renewal duplicated customer ownership; bank account and import batch parent models; policy-number uniqueness scope and normalization; shared/invalid NationalCode/mobile handling; marketer manual-assignment lifecycle; payment/bank matching tolerance and collision rules; canonical match-status and renewal-status domains; candidate-key scopes; debit/credit and timestamp semantics; default/Required rules; numeric limits and commission precision; and cascade/deletion policy. No relationship or unique index depending on these decisions is authorized before sign-off.

## 7. Recommended execution order and acceptance gates

1. **Preserve and discover:** DB-01/02; backup, live export, profiles, exceptions.
2. **Remove import blockers:** DB-03/04; prove lossless field capacity and session isolation.
3. **Stabilize parent model:** DB-05, then core policies/installments DB-06/07.
4. **Resolve dependent integrity:** DB-08/09, but stop at DB-10 until bank rules are approved.
5. **Add Phase 4 lookup indexes:** DB-11/12/13 using normal—not speculative unique—indexes.
6. **Access gate:** DB-14 rehearsal, rollback, compact/reopen, fixture import, row-count and financial-total comparison. Only then may Phase 4 start.
7. **Production performance/integrity:** DB-15 through DB-24 in order after query/business evidence.
8. **Deferred maintainability:** DB-25 through DB-28 only with dependency scans.

Acceptance for every package: zero unexplained row-count/financial-total changes; zero new orphans/duplicates; exception disposition signed; actual Access index/relationship properties match the manifest; application/import smoke tests pass; timings are not materially worse; backup restore is demonstrated; and rollback remains available through sign-off.
